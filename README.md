## What is this?
Boot2Flipper is an application for Flipper Zero that allows you to emulate a iPXE USB thumb drive.  

## Features
* Automatic `autoexec.ipxe` script generation
  - Configure IP address, netmask, gateway and DNS server on your Flipper Zero
  - Pick the network interface, or ask for it on the Flipper while booting
  - Then chainload a URL (with arguments), run an iPXE script from the SD card, drop to the iPXE shell, or type iPXE commands on the Flipper
* UEFI and Legacy BIOS support
* Profiles on the SD card, saved as you change settings
* Boot progress, the host's system information (SMBIOS) and a log file of the boot on the Flipper
* Support for custom iPXE EFI executable

## How does it work?
Boot2Flipper emulates a USB Mass Storage device with "virtual" FAT32 filesystem.
The Boot2Flipper application generates FAT32 File Allocation Table and `autoexec.ipxe` script and iPXE EFI Executable on the fly.  

When the file itself is requested, Boot2Flipper automatically calculates the offset from the each file's cluster number and returns the file content from the underlying flipper filesystem.  

For legacy BIOS boot, the MBR contains a small boot loader ([`tools/bios_boot/boot.S`](tools/bios_boot/boot.S)) that loads `ipxe.lkrn` and passes the generated script to it as the kernel command line, which iPXE runs on startup, and the `.B2F` writer as the initrd. The command line can be up to 8191 bytes: `ipxe.lkrn` advertises 2047, but iPXE copies all of it, and the loader has the rest of the kernel's real-mode segment for it. A longer script is passed as the initrd, without the writer. Since the disk layout is generated by Boot2Flipper, the file locations are patched into the loader instead of parsing FAT.  
If you modify the loader, run `tools/bios_boot/build.sh` to regenerate `src/disk/bios_boot_image.h`.  

### Talking to the Flipper from the host (`.B2F`)
The root directory is at LBA 0x2000, and 0x2001-0x20FF is reserved for a hidden `.B2F` directory and its files, each sized to its content (other files start at 0x2100). A program on the booted machine can use them with raw sector reads and writes, without parsing FAT:

| File | LBA | Size | Content |
| --- | --- | --- | --- |
| `.B2F/info` | 0x2002 | 512 bytes | Read-only header, starts with the magic `B2F INFO` (see below) |
| `.B2F/status` | 0x2003 | 512 bytes | ASCII text shown in `status` mode, up to the first NUL (3 lines) |
| `.B2F/frame` | 0x2004 | 1024 bytes | 128x64 1-bit image shown full screen in `framebuffer` mode. Rows of 16 bytes, least significant bit is the leftmost pixel (XBM), 1 is black |
| `.B2F/mode` | 0x2006 | 512 bytes | What the Flipper shows, an ASCII word: `status` (default, also for unknown words), `framebuffer` or `prompt` (asks `.B2F/prompt/`, the Flipper writes `status` back once answered) |
| `.B2F/sysinfo` | 0x2007 | 512 bytes | The host's system information, `key=value` lines up to the first NUL. The Flipper shows `manufacturer`, `product`, `serial`, `uuid`, `platform` and `arch` |
| `.B2F/log` | 0x2008 | 512 bytes | Every write is a line (up to the first NUL) for the Flipper's log file, if `Write log` is on |
| `.B2F/prompt/type` | 0x2011 | 512 bytes | `choice` (a list, the default), `confirm` (two buttons) or `text` |
| `.B2F/prompt/question` | 0x2012 | 512 bytes | The question. Lists and keyboards show its first line |
| `.B2F/prompt/options` | 0x2013 | 1024 bytes | One per line. Confirm: the positive (OK key) then the negative (Back key) button, Yes/No if none, only OK if one. Text: the default. A choice without options is a Yes/No confirm |
| `.B2F/prompt/kbdtype` | 0x2015 | 512 bytes | Keyboard for `text`: `text` (default), `ip` or `number` |
| `.B2F/prompt/timeout` | 0x2017 | 512 bytes | Seconds to answer, counted down on the Flipper until a key is pressed there. Empty or `0` waits forever |
| `.B2F/prompt/answer` | 0x2016 | 512 bytes | Read-only. `pending\n` while asking, then `ok\n<value>\n` (the option or text), `cancel\n` (Back on the Flipper, except on a confirm with a Back button) or `timeout\n` |
| `.B2F/prompt/script` | 0x2018 | 512 bytes | The answer as an iPXE script, `#!ipxe\n<value>\n` padded with newlines (`exit 1` if not answered). UEFI caches what it read through its FAT driver, so `b2f.efi script` writes it again through the file system before iPXE chains it |

The LBAs are the same for every boot method. To find the disk (or the area, if the layout ever changes), look for the magic in `info`. Its layout, little-endian:

| Offset | Size | Content |
| --- | --- | --- |
| 0 | 8 | `B2F INFO` |
| 8 | 2 | Version (1) |
| 10 | 2 | Entry count |
| 16 | 32 each | Entry: name (16, NUL padded), LBA (4), size in bytes (4), flags (4, bit 0 = writable), reserved (4) |

Write the frame's 2 sectors in one command, so it isn't shown half updated. The writers are in `.B2F/bin` from 0x2020, the sectors before it are kept for more files.  
To ask the user without the writers: write the prompt files, write `prompt` to the mode, then read the answer sector until it is not `pending` (raw reads, so no cache gets in the way).  
Other writes don't change the disk: the free space is marked as bad clusters, so operating systems see a full disk and can't add files, and writes outside `.B2F` are dropped.

#### From iPXE
The generated script sets `${b2f}` to a writer on the disk (`.B2F/bin/b2f.efi` on UEFI, `.B2F/bin/b2f.pxe` on BIOS), so a chainloaded script can use:

```
imgexec ${b2f} status Downloading kernel...\nPlease wait
imgexec ${b2f} frame logo.bin
imgexec ${b2f} mode framebuffer
imgexec ${b2f} clear
imgexec ${b2f} sysinfo platform=${platform}\narch=${buildarch}\nproduct=${product}
imgexec ${b2f} log Kernel downloaded
```

`imgexec -q ${b2f} ...` leaves out iPXE's `file:/.B2F/bin/b2f.efi... ok` line. The `-q` can't be put in `${b2f}`: iPXE expands a variable to one argument.  
On BIOS, iPXE runs the writer (a PXE image) only with an open network interface, so the generated script runs `ifopen` when it sets `${b2f}`.

To ask the Flipper's user, fill in the prompt and run `prompt`, which waits for the answer. `${${b2f_answer}}` is the answer (the generated script points `${b2f_answer}` at where the writer left it). If the user pressed Back or the timeout ran out, `prompt` fails and the answer is `cancel` or `timeout`:

```
imgexec ${b2f} question Which OS?
imgexec ${b2f} options Ubuntu|Debian|Windows
imgexec ${b2f} prompt choice && set os ${${b2f_answer}} || goto cancelled

imgexec ${b2f} question Server IP
imgexec ${b2f} options 192.168.0.10
imgexec ${b2f} kbdtype ip
imgexec ${b2f} prompt text && set server ${${b2f_answer}} || goto cancelled

imgexec ${b2f} question Reinstall the OS?\nAll data will be erased.
imgexec ${b2f} options Erase|Keep
imgexec ${b2f} prompt confirm && set choice ${${b2f_answer}} || goto cancelled

imgexec ${b2f} question Boot Ubuntu?
imgexec ${b2f} options
imgexec ${b2f} timeout 10
imgexec ${b2f} prompt confirm || goto ${${b2f_answer}}
goto ${${b2f_answer}}
:Yes
:timeout
echo Booting Ubuntu, also when nobody answered
```

The timeout stops once a key is pressed on the Flipper, and stays set for later prompts until `timeout 0`.

To run a command typed on the Flipper (`prompt text`), BIOS has `imgexec ${b2f} exec`, which runs the answer with `PXENV_FILE_EXEC`; UEFI has `imgexec ${b2f} script && chain --autofree file:/.B2F/prompt/script`. This is what the `F.shell` target does. On BIOS a typed command can't run `${b2f}` itself, as the writer is the image running it.

`\n` starts a new line. `clear` empties the status and frame and goes back to `status` mode. For `frame`, UEFI reads an image fetched with `imgfetch http://server/logo.bin logo.bin`, BIOS opens the given URI (e.g. `http://server/logo.bin`).
Chainloaded scripts can use `${b2f}` too. On BIOS the writer is an image iPXE got at boot, so an `imgfree` of all images removes it: free images by name (`imgfree <name>`), or write to the Flipper before `imgfree`. On UEFI each call runs `b2f.efi` from the disk and leaves an 8.6KB image until the next `imgfree`.  
This needs the `-legacy` iPXE builds: the current `ipxe.efi` and `ipxe.lkrn` take over the USB controller, so the Flipper's disk is gone once iPXE runs (booting still works, the writer then fails with an error).
The writers are built with `tools/b2f_efi/build.sh` and `tools/b2f_pxe/build.sh`.

## Usage
### How to setup iPXE files?
1. Install Boot2Flipper on your Flipper Zero
2. Open `Boot2Flipper` application on your Flipper Zero
3. Open `qFlipper` or other file transfer application (e.g. [`f0-mtp`](https://github.com/Alex4386/f0-mtp))
4. Head to `SD Card` -> `apps_data` -> `boot2flipper`
5. Create `ipxe` directory
6. Download [`ipxe.efi`](https://boot.ipxe.org/x86_64-efi/ipxe.efi) and [`ipxe.lkrn`](https://boot.ipxe.org/ipxe.lkrn) from [boot.ipxe.org](https://boot.ipxe.org) and put them into `ipxe` directory.
   To show status on the Flipper from iPXE (see [`.B2F`](#talking-to-the-flipper-from-the-host-b2f)), use [`ipxe-legacy.efi`](https://boot.ipxe.org/x86_64-efi/ipxe-legacy.efi) and [`ipxe-legacy.lkrn`](https://boot.ipxe.org/ipxe-legacy.lkrn) instead, renamed to `ipxe.efi` and `ipxe.lkrn`.

### How to use Boot2Flipper?
1. Open `Boot2Flipper` application on your Flipper Zero. It opens the profile you used last.
2. The first screen shows the profile: its network, boot method and what runs after the network is up (long ones scroll). It warns if the iPXE files are missing.
   Press `◀` for the settings, `OK` to start, `Back` to exit.
3. In `Settings` (changes are saved to the profile when you go back):
   * `Profile`: load another profile, save the settings as a new one, or delete one.
   * `Network`: `DHCP` or `Static`. For `Static`, set the IP address, netmask, gateway and DNS server in `IP Settings`.
     All four octets are edited on one screen: type the digits and it moves to the next octet once no more digits fit (e.g. after `192` or `0`), or use the `◀`/`▶` buttons to move between octets. Typing replaces a newly focused octet, the backspace key deletes into the previous octet, and long press OK on it clears all.
   * `Then Run`: what iPXE does once the network is up.
     * `URL`: chainloads `URL` with `Arguments` (e.g. a kernel command line).
       The URL keyboard has `.`, `/`, `:`, `-` on the letter layers; the `ABC`/`123`/`abc` key switches to uppercase and digits/symbols, and long press on it types a space. Long press OK types the other case, long press the backspace key clears the text. Press `save` when done.
     * `Script`: runs an iPXE script from the SD card (`Script File`). UEFI chains it from the disk as `CHAIN.IPXE`, BIOS runs it as part of the generated script.
     * `Shell`: drops to the iPXE shell.
     * `F.shell`: asks for iPXE commands on the Flipper and runs them, showing `OK` or `Failed` with the command (variables expanded, e.g. `echo ${net0/ip}`) above the next one. Back leaves to the iPXE shell.
   * `Boot Method`: `Hybrid` (default) boots on both legacy BIOS and UEFI.
     `UEFI` is a spec-compliant GPT disk with a protective MBR, `MBR` is an MBR-only disk.
     If your UEFI firmware doesn't detect the disk in `Hybrid`, switch to `UEFI`.
   * `Advanced`:
     * `Net Interface`: `auto` (DHCP on any interface, static IP on `net0`), `ask` (lists the interfaces as `net0 (UP, <MAC>)` on the Flipper while booting, all of them if not answered in 30 seconds), or an interface. OK types any name.
     * `Status report`: shows each step on the Flipper (e.g. `Setting IP address to 192.168.1.10`).
     * `b2f imgexec`: `quiet` runs the writer with `imgexec -q`, so iPXE doesn't print a line for each call.
     * `Collect sysinfo`: sends the host's platform (`pcbios`/`efi`), architecture and SMBIOS manufacturer, product, serial number and UUID to the Flipper. Press `▶` while running to see them.
     * `Write log`: keeps a log of the boot in `apps_data/boot2flipper/logs/<date>_<time>.log`: the settings, status changes, prompts and answers, the system information, and every interface (MAC, IP, netmask, gateway) and the DHCP results once the network is up.
4. Press `OK` on the first screen to start emulating the USB Mass Storage device.
5. On your PC, Select Boot Device labelled as `FLIPPER Boot2Flipper 1.0` or similar.
6. Your Flipper Zero will report as it is reading `ipxe.lkrn` or `bootx64.efi` file., due to flipper zero's limitation, it will take some time to read and send the file to PC.
7. Congratulations, You'll see iPXE booting up on your PC!

## FAQ
1. **Why didn't you use other sizes less than `128MB`?**  
   This is due to some BIOSes not respecting `ESP` partition sizes that are less than `100MB`.
   This is a known issue with some UEFI implementations. Due to this, if you have Debug logging enabled in Flipper Zero, initial FAT32 FAT scan may take a while. So either disable Debug logging or wait.
